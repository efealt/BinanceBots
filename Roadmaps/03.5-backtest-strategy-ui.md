# Phase 3.5 — Backtest Strategy UI Roadmap

## Objective

Expose the completed backend Backtest engine through the authenticated Backtest page so the user can configure, launch, monitor, and inspect real historical strategy runs against the Render-resident SQLite data.

This phase remains historical Backtest only. It does not add Paper mode, Binance account access, or real order submission.

## Rules

- The browser is configuration and presentation only. Backtest execution runs on the Render backend and continues if the browser disconnects.
- The existing top-page dataset selector is the sole symbol/dataset selector.
- The existing top-page chart interval selector is the sole Backtest replay interval selector.
- Do not ask for symbol, dataset, or timeframe again in the lower Backtest form.
- Stored 1-minute data is aggregated on the backend to the selected UTC replay interval when 1-hour or 1-day is selected.
- Strategy logic remains in the shared mode-neutral strategy interface. The UI/API must not duplicate strategy logic.
- Phase 3.5 exposes the existing Phase 3 static-grid fixture only; it does not invent additional strategies.
- The grid fixture is explicitly identified as an engineering/static grid: it places its configured initial resting levels once and does not optimize or replenish them.
- Backtest jobs are backend-owned background work, not long-held browser HTTP requests.
- Only one heavy Backtest job may run at a time on the current small Render instance.
- Progress must be visible from 0% to 100%. The browser polls lightly (seconds, not milliseconds).
- Every API route is behind the existing server-side authentication middleware.
- Canonical Phase 1 run/order/fill/position/equity persistence remains the result source of truth.
- No Paper or Live order path is enabled.

## Implementation

### 3.5.1 — Backend replay interval

- [ ] Add an explicit Backtest replay interval to the run configuration.
- [ ] Support UTC 1m, 1h, and 1d replay from stored 1m OHLCV.
- [ ] Aggregate OHLCV deterministically on the backend.
- [ ] Preserve the pre-first-active-candle rule required by `on_start`; if the requested range begins before any prior replay candle exists, reserve the first available replay candle as pre-roll and begin active replay on the next candle.
- [ ] Record requested interval/range and effective active range in run metadata.

### 3.5.2 — Background Backtest job API

- [ ] Add authenticated create/status/result endpoints under `/api/backtests`.
- [ ] Launch synchronous Rust replay inside a backend-owned blocking task.
- [ ] Track queued/running/completed/failed state and integer progress.
- [ ] Update progress by replayed-candle percentage, not high-frequency ticks.
- [ ] Reject concurrent heavy jobs while one is running.
- [ ] Return a compact persisted-run summary including run ID, candles, fills/orders, final equity, return, fees, realized/unrealized PnL, position, and max drawdown.

### 3.5.3 — Real Backtest configuration UI

- [ ] Replace the old dummy Inputs card.
- [ ] Reuse the top dataset and interval selectors rather than duplicating them.
- [ ] Show the selected dataset/interval as read-only context.
- [ ] Add start/end date controls, initial capital, static-grid parameters, and execution assumptions.
- [ ] Validate inputs before submit.
- [ ] Make the Run Backtest button call the authenticated backend job API.
- [ ] Disable incompatible controls while a job is active.

### 3.5.4 — Progress and result UI

- [ ] Replace the old dummy Output card.
- [ ] Show job status, run ID, and a visible 0–100% progress bar.
- [ ] Poll status at a light interval (about 2–3 seconds), with an immediate first status check.
- [ ] On completion show compact KPI cards and a complete fill audit for the current static-grid fixture.
- [ ] On failure show the backend error clearly and re-enable the form.
- [ ] Keep the browser independent from execution; navigating away must not stop the backend job.

### 3.5.5 — Verification

- [ ] Unit-test backend aggregation and pre-roll timing.
- [ ] Unit-test job request validation/result summarization where practical.
- [ ] Run the existing core trading suite and full frozen XAGUSDT regression.
- [ ] Deploy to Render.
- [ ] Invoke a real authenticated production backtest through the new backend endpoint/UI and verify it reads the Render-resident dataset, reaches 100%, persists a canonical run, and returns coherent results.
- [ ] Verify no Paper or real-order functionality is enabled.

## Completion condition

Phase 3.5 is complete when the hosted Backtest page can launch the Phase 3 static grid against the dataset and interval selected at the top of the page, execution occurs on Render as a backend-owned job, the user sees 0–100% progress with light polling, and the completed persisted run is inspectable in the rebuilt result area.

After this checkpoint, the next master phase is Phase 4 — Live Paper runtime.
