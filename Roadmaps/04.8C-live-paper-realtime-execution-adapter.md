# Phase 4.8C — Live-Paper Real-Time Execution Adapter

## Objective

Correct the Live-Paper execution architecture without duplicating strategy code.

The permanent rule is:

> **One shared strategy implementation produces order intents. Backtest and Live-Paper use different execution adapters because they observe different market data. Fills then flow through the same portfolio/accounting and canonical persistence path.**

Live-Paper is **not** a Backtest loop running against live candles. Once a simulated order is resting, its execution must be driven by real Binance market events immediately. Candle completion remains relevant only to strategies that explicitly make candle-close decisions.

This roadmap is a correctness blocker before the remaining Console/production-acceptance work.

## Non-negotiable architecture

```text
                         SHARED STRATEGY
                    Strategy / StaticGridStrategy
                              |
                              | StrategyOrderIntent
                              v
                  +-----------+-----------+
                  |                       |
                  v                       v
       Backtest execution          Live-Paper execution
       historical bars/ticks       real Binance events
                  |                       |
                  +-----------+-----------+
                              |
                              v
                       canonical Fill
                              |
                              v
                  shared portfolio/accounting
                              |
                              v
                  shared Run/order/fill storage
```

### Shared across modes

- Strategy implementation and parameters.
- `StrategyOrderIntent` contract.
- Order identity/state model.
- Fill representation after an executor decides a fill occurred.
- Portfolio/inventory/PnL/fee accounting.
- Canonical Run / Decision / OrderIntent / Order / Fill / Position / Equity persistence.
- Bot → Run ownership and Trading-page monitoring contracts.

### Intentionally mode-specific

- **Backtest execution:** historical OHLC/tick interpretation and its unavoidable intrabar assumptions.
- **Live-Paper execution:** real-time Binance trade/quote event handling.
- **Future Live-Real-Account execution:** actual Binance order submission, acknowledgement, reconciliation, and exchange fills.

Do **not** duplicate `StaticGridStrategy` or any future strategy to achieve this split.

## Phase 1 — Execution contract split

- [x] Refactor the current generic `SimulatedExecution` responsibility into explicit execution paths rather than forcing Backtest and Live-Paper through one candle-oriented implementation.
- [x] Keep `Strategy`, `StrategyStartContext`, `StrategyContext`, and `StrategyOrderIntent` mode-neutral.
- [x] Define one shared fill/result contract consumed by portfolio accounting and persistence regardless of which executor produced it.
- [x] Preserve the current Backtest bar-based semantics exactly behind a clearly named historical execution adapter.
- [x] Add a separate Live-Paper execution adapter API that accepts real-time market events and owns resting simulated orders.
- [x] Avoid compatibility layers or duplicated strategy wrappers; change the internal API directly where clearer.
- [x] Add tests proving the same `StaticGridStrategy` output is submitted unchanged to either execution path.

**Implemented:** `SimulatedExecution` was removed from the internal API. `HistoricalExecution` now owns the unchanged candle/OHLC Backtest semantics. `LivePaperExecution` owns its own resting-order book API and accepts `LiveExecutionEvent::Trade` events. Both produce the same shared `ExecutionFill` contract and both accept the exact same `StrategyOrderIntent` objects. The common pending-order mechanics, latency eligibility, partial-fill accounting, fee calculation, and fill-result construction remain centralized rather than copied between adapters. At the Phase 1 checkpoint the running Live-Paper runtime was intentionally not wired yet. Phase 3 now uses the live-event adapter for resting-order execution while Backtest remains on HistoricalExecution.

**Checkpoint:** Strategy logic is shared once; only execution interpretation differs by mode.

## Phase 2 — Lossless real-time Binance execution feed

The current Market service already receives Binance trades, quotes, order-book updates, and candles. Live-Paper execution must consume those events directly rather than periodically inspecting a completed candle.

- [x] Add backend event delivery from the existing Market service to interested runtimes using a bounded broadcast/subscription contract.
- [x] Provide Live-Paper with **trade events as they arrive**, including exchange trade ID, trade time, price, and quantity.
- [x] Keep candle events available independently for strategy clocks such as `on_candle`.
- [x] Do not use browser WebSockets as an execution source; the Render backend owns the feed and runtime.
- [x] Track the last processed trade/event identity per Run so duplicate market events cannot create duplicate fills.
- [x] Define reconnect/gap behavior explicitly:
  - no silent assumption that missed real-time trades did not touch a resting order;
  - pause/fail or recover continuity when a gap cannot be proven safe;
  - persist the reason when chronology is uncertain.
- [x] Ensure the event path is fast enough that Live-Paper does not depend on the 500 ms runtime snapshot polling loop for fills.

**Implemented:** The backend Market feed now publishes a bounded per-symbol realtime event stream for feed status, Binance trades, and candle updates. Each event has a monotonic backend sequence, connection epoch, and backend receive timestamp. Every Live-Paper Run now owns a `RunMarketSubscription` created before its initial resting orders are submitted. The subscription tracks its own last sequence and last Binance trade ID, suppresses exact duplicate trade IDs, and turns lag, sequence gaps, backwards trade IDs, closed channels, or connection-epoch changes into explicit continuity failures. A realtime feed disconnect terminates the current development Run with a persisted failure reason because missed trades cannot yet be proven recoverable. Trade/candle events arrive directly through the backend subscription rather than the 500 ms snapshot polling loop. Phase 3 now consumes those trade events for resting-order execution.

At the user's request, migration 007 also resets disposable development trading state before this architecture proceeds. It removes Bot/Run operational records only; downloaded historical data remains intact.

**Checkpoint:** A running Bot can receive each backend Binance trade event directly and in auditable order, independent of the UI and candle-close cycle.

## Phase 3 — Live-Paper resting-order execution

Implement real-time simulated exchange behavior on top of Phase 2.

### Limit orders

- [x] Once an order exists and is eligible, evaluate every qualifying live Binance trade immediately.
- [x] **Touch / BUY:** fill when a post-eligibility trade price is `<= limit price`.
- [x] **Touch / SELL:** fill when a post-eligibility trade price is `>= limit price`.
- [x] **Trade Through / BUY:** require trade price `< limit price`.
- [x] **Trade Through / SELL:** require trade price `> limit price`.
- [x] Use the resting limit price as the simulated fill price for the current Paper model; do not invent price improvement unless a later execution model explicitly adds it.
- [x] Record the actual qualifying Binance trade time/identity in fill metadata for auditability.

### Simulation assumptions

- [x] `latency_ms` controls only when a newly submitted simulated order becomes eligible; it must never imply a candle-close wait.
- [x] `partial_fill_ratio` remains an explicit simulation assumption. Each qualifying event may fill at most `original_quantity * partial_fill_ratio`, capped by remaining quantity, until the order is complete.
- [x] Apply configured fees through the same shared accounting path.
- [x] Keep market-order behavior explicit and tested; if the current strategy does not require it, do not let market-order work delay correct limit-order grid execution.

### Safety

- [x] Never allow a trade whose exchange timestamp precedes `eligible_from_ms` to fill the order.
- [x] Never process the same Binance trade twice for one Run.
- [x] Stopping a Run immediately disables further simulated fills.
- [x] Feed uncertainty must not create guessed fills.

**Implemented:** Live-Paper now owns `LivePaperExecution` directly. Binance trade events are converted to `LiveTradeEvent` and evaluated immediately against resting simulated orders. Touch and Trade Through use the documented inclusive/strict inequalities, fill at the resting limit price, honor latency and partial-fill assumptions, apply shared fee/accounting logic, and persist the qualifying Binance trade ID plus exchange/receive timestamps. Duplicate trade IDs are suppressed both by the per-Run market subscription and defensively by the executor; backwards IDs fail instead of guessing chronology. Completed candles no longer create Live-Paper fills and are reserved for strategy timing. Stop/fail expires the executor's pending orders and the core rejects later trade processing.

**Checkpoint:** A resting Live-Paper grid order fills on the qualifying live trade event, without waiting for a candle to close.

## Phase 4 — Paper runtime integration and serialized chronology

A Bot may receive live trades and completed strategy candles concurrently. State mutation must remain deterministic.

- [x] Refactor each Live-Paper Run around one serialized backend event loop/actor that owns:
  - execution order state;
  - strategy state;
  - portfolio state;
  - canonical persistence ordering.
- [x] Route real-time **trade events** to the Live-Paper executor immediately.
- [x] Route **completed strategy candles** separately to `strategy.on_candle`.
- [x] Route `on_start` order intents immediately into the Live-Paper executor.
- [x] When the executor produces a fill:
  1. persist Fill / OrderState;
  2. apply it to the shared portfolio;
  3. persist Position / Equity effects;
  4. update the runtime snapshot/UI stream.
- [x] Define deterministic ordering for market events that share timestamps and preserve canonical `run_sequence`.
- [x] Keep Bot concurrency and one-active-Run-per-Bot guarantees unchanged.
- [x] Keep immediate Start semantics from Phase 5C: the initial grid is created immediately from completed information, after which its resting orders are live-event driven.
- [x] Do not change Backtest chronology in this phase.

### Future strategy hook

- [x] Design the runtime boundary so a later shared `strategy.on_fill(...)` hook can be added once for strategies that replenish/recenter after fills.
- [x] Do **not** invent replenishment rules for the current static-grid fixture; it still places its initial grid once.

**Implemented:** Each Live-Paper Run is now one serialized backend actor. The backend market subscription is the canonical market-event clock: trades and Binance 1-minute candle events enter through the same monotonic backend `sequence`, so equal exchange timestamps are ordered by backend arrival sequence and the resulting canonical `run_sequence` is deterministic. Trade events go straight to `LivePaperExecution`; only closed candle events advance the replay aggregator and call `strategy.on_candle`. The 500 ms timer remains only for non-canonical UI market snapshots and cannot create fills or strategy decisions. `on_start` still creates and submits the initial grid immediately. Fill effects are persisted in the explicit order Fill → OrderState → portfolio/accounting → Position → Equity, then the runtime snapshot is published. The fill boundary now has one documented insertion point for a future shared `strategy.on_fill(...)` hook, but no replenishment/recentering behavior was added. Backtest chronology and one-active-Run-per-Bot admission are unchanged.

**Checkpoint:** Live-Paper strategy decisions and live order execution have separate clocks but one deterministic Run state machine.

## Phase 5 — Backtest isolation, tests, and parity rules

Backtest remains a historical simulator. It should not be distorted to imitate real-time Paper limitations, and Live-Paper should not be degraded to candle execution merely to preserve old fill parity.

- [x] Leave the current Backtest historical bar executor behavior unchanged:
  - resting BUY limit + candle low touch => fill under Touch;
  - resting SELL limit + candle high touch => fill under Touch;
  - historical fill timing remains limited by the available dataset.
- [x] Keep future historical **tick-data execution** as a separate optional Backtest adapter that can be added later without changing strategy code.
- [x] Update automated parity tests so they compare what should actually be common:
  - strategy decisions for identical strategy information;
  - order intents/configuration;
  - accounting given identical fills;
  - persistence invariants.
- [x] Stop requiring candle-based Paper fills to match Backtest fill timing when Paper has richer live event information.
- [x] Add focused Live-Paper tests for:
  - immediate Touch fill before candle close;
  - Trade Through strict inequality;
  - latency eligibility;
  - partial fills across qualifying events;
  - no pre-eligibility fill;
  - duplicate-trade suppression;
  - stop prevents later fills;
  - reconnect/gap failure/recovery contract.
- [x] Keep the full frozen XAGUSDT Backtest regression unchanged and green.
- [x] Add a deterministic synthetic test where the same static-grid strategy creates identical initial order intents in Backtest and Live-Paper, while the two executors legitimately determine fills from their own data source.

**Implemented:** Backtest remains on the unchanged historical bar executor and the frozen XAGUSDT regression is still the production regression gate. Phase 5 verification now explicitly separates shared semantics from mode-specific execution clocks: strategy decisions/order intents and accounting/persistence invariants remain comparable, while Live-Paper fill timing is driven by real trade events and historical fills remain limited by candle information. Focused `phase5_` tests cover intrabar Touch, Trade Through strictness, latency/no-pre-eligibility fills, partial fills, duplicate suppression, stop behavior, feed lag/reconnect/sequence-gap failure, and fresh-subscription recovery. A deterministic static-grid test submits the exact same initial intents to both adapters, then proves the historical executor fills at candle-close knowledge time while Live-Paper fills earlier on qualifying trades. Any future historical tick simulator remains a separate Backtest execution adapter rather than a change to strategy code.

**Checkpoint:** Tests prove shared strategy semantics without falsely forcing Backtest and Live-Paper execution clocks to be identical.

No major Trading-page redesign is required. The UI should simply reflect fills when the backend actually creates them.

- [ ] Production smoke test with an order level intentionally close enough to market to observe a real qualifying Touch.
- [ ] Compare the qualifying Binance trade timestamp with the persisted fill timestamp and confirm the fill occurred before the candle close when the touch happened intrabar.
- [x] Verify browser close/reopen does not affect execution.
- [x] Run two different Live-Paper Bots concurrently and verify no cross-Run trade/fill contamination.
- [x] Update `Documents/ARCHITECTURE.md` after implementation with the final **shared strategy → mode-specific executor → shared accounting/persistence** architecture.

**Implementation status:** Phase 6 UI/backend integration is wired and automated verification is in place. Runtime fill snapshots update chart/order/portfolio state directly, and a new fill signature bypasses the normal 2-second Run Activity presentation throttle so activity reloads from the same persisted fill event. The UI explicitly states that resting limits react to qualifying Binance trades immediately; latency is only an eligibility delay and partial-fill ratio only controls simulated fill size. Existing backend tests prove browser subscriptions do not own runtimes and two Bot cores remain isolated. The remaining acceptance items are the hosted production Touch smoke test and timestamp comparison, which also visually confirm the active grid line/fill marker/Position/PnL/Open Orders/Run Activity response.

**Checkpoint:** The hosted Live-Paper grid behaves like a simulated live exchange account: resting orders react to live Binance events immediately, while strategy candle logic remains independent.

## Final acceptance

This roadmap is complete only when all of the following are true:

1. There is still exactly **one** implementation of the current static-grid strategy.
2. Backtest continues to use historical execution assumptions appropriate to its historical data.
3. Live-Paper no longer waits for candle close to execute resting grid orders.
4. Artificial execution behavior in Live-Paper comes only from explicitly configured assumptions such as latency, partial fills, fees, or fill policy.
5. Strategy-generated order intents, resulting fills, portfolio accounting, and canonical persistence remain auditable through the same shared contracts.
6. The frozen historical Backtest regression remains unchanged.
7. Phase 6 Console work and final Phase 4 production acceptance resume only after this execution-correctness roadmap passes.
