# Phase 4.8C — Live-Paper Real-Time Execution Adapter

## Objective

Correct the Live-Paper execution architecture without duplicating strategy code.

The permanent rule is:

> **One shared strategy implementation produces order intents. Backtest and Live-Paper use different execution adapters because they observe different market data. Fills then flow through the same portfolio/accounting and canonical persistence path.**

Live-Paper is **not** a Backtest loop running against live candles. Once a simulated order is resting, its execution must be driven by real Binance market events immediately. Candle completion remains relevant only to strategies that explicitly make candle-close decisions.

This roadmap is a correctness blocker before the remaining Console/production-acceptance work.

## Non-negotiable architecture

```text
                         SHARED STRATEGY
                    Strategy / StaticGridStrategy
                              |
                              | StrategyOrderIntent
                              v
                  +-----------+-----------+
                  |                       |
                  v                       v
       Backtest execution          Live-Paper execution
       historical bars/ticks       real Binance events
                  |                       |
                  +-----------+-----------+
                              |
                              v
                       canonical Fill
                              |
                              v
                  shared portfolio/accounting
                              |
                              v
                  shared Run/order/fill storage
```

### Shared across modes

- Strategy implementation and parameters.
- `StrategyOrderIntent` contract.
- Order identity/state model.
- Fill representation after an executor decides a fill occurred.
- Portfolio/inventory/PnL/fee accounting.
- Canonical Run / Decision / OrderIntent / Order / Fill / Position / Equity persistence.
- Bot → Run ownership and Trading-page monitoring contracts.

### Intentionally mode-specific

- **Backtest execution:** historical OHLC/tick interpretation and its unavoidable intrabar assumptions.
- **Live-Paper execution:** real-time Binance trade/quote event handling.
- **Future Live-Real-Account execution:** actual Binance order submission, acknowledgement, reconciliation, and exchange fills.

Do **not** duplicate `StaticGridStrategy` or any future strategy to achieve this split.

---

## Phase 1 — Execution contract split

- [ ] Refactor the current generic `SimulatedExecution` responsibility into explicit execution paths rather than forcing Backtest and Live-Paper through one candle-oriented implementation.
- [ ] Keep `Strategy`, `StrategyStartContext`, `StrategyContext`, and `StrategyOrderIntent` mode-neutral.
- [ ] Define one shared fill/result contract consumed by portfolio accounting and persistence regardless of which executor produced it.
- [ ] Preserve the current Backtest bar-based semantics exactly behind a clearly named historical execution adapter.
- [ ] Add a separate Live-Paper execution adapter API that accepts real-time market events and owns resting simulated orders.
- [ ] Avoid compatibility layers or duplicated strategy wrappers; change the internal API directly where clearer.
- [ ] Add tests proving the same `StaticGridStrategy` output is submitted unchanged to either execution path.

**Checkpoint:** Strategy logic is shared once; only execution interpretation differs by mode.

---

## Phase 2 — Lossless real-time Binance execution feed

The current Market service already receives Binance trades, quotes, order-book updates, and candles. Live-Paper execution must consume those events directly rather than periodically inspecting a completed candle.

- [ ] Add backend event delivery from the existing Market service to interested runtimes using a bounded broadcast/subscription contract.
- [ ] Provide Live-Paper with **trade events as they arrive**, including exchange trade ID, trade time, price, and quantity.
- [ ] Keep candle events available independently for strategy clocks such as `on_candle`.
- [ ] Do not use browser WebSockets as an execution source; the Render backend owns the feed and runtime.
- [ ] Track the last processed trade/event identity per Run so duplicate market events cannot create duplicate fills.
- [ ] Define reconnect/gap behavior explicitly:
  - no silent assumption that missed real-time trades did not touch a resting order;
  - pause/fail or recover continuity when a gap cannot be proven safe;
  - persist the reason when chronology is uncertain.
- [ ] Ensure the event path is fast enough that Live-Paper does not depend on the 500 ms runtime snapshot polling loop for fills.

**Checkpoint:** A running Bot can receive each backend Binance trade event directly and in auditable order, independent of the UI and candle-close cycle.

---

## Phase 3 — Live-Paper resting-order execution

Implement real-time simulated exchange behavior on top of Phase 2.

### Limit orders

- [ ] Once an order exists and is eligible, evaluate every qualifying live Binance trade immediately.
- [ ] **Touch / BUY:** fill when a post-eligibility trade price is `<= limit price`.
- [ ] **Touch / SELL:** fill when a post-eligibility trade price is `>= limit price`.
- [ ] **Trade Through / BUY:** require trade price `< limit price`.
- [ ] **Trade Through / SELL:** require trade price `> limit price`.
- [ ] Use the resting limit price as the simulated fill price for the current Paper model; do not invent price improvement unless a later execution model explicitly adds it.
- [ ] Record the actual qualifying Binance trade time/identity in fill metadata for auditability.

### Simulation assumptions

- [ ] `latency_ms` controls only when a newly submitted simulated order becomes eligible; it must never imply a candle-close wait.
- [ ] `partial_fill_ratio` remains an explicit simulation assumption. Each qualifying event may fill at most `original_quantity * partial_fill_ratio`, capped by remaining quantity, until the order is complete.
- [ ] Apply configured fees through the same shared accounting path.
- [ ] Keep market-order behavior explicit and tested; if the current strategy does not require it, do not let market-order work delay correct limit-order grid execution.

### Safety

- [ ] Never allow a trade whose exchange timestamp precedes `eligible_from_ms` to fill the order.
- [ ] Never process the same Binance trade twice for one Run.
- [ ] Stopping a Run immediately disables further simulated fills.
- [ ] Feed uncertainty must not create guessed fills.

**Checkpoint:** A resting Live-Paper grid order fills on the qualifying live trade event, without waiting for a candle to close.

## Phase 4 — Paper runtime integration and serialized chronology

A Bot may receive live trades and completed strategy candles concurrently. State mutation must remain deterministic.

- [ ] Refactor each Live-Paper Run around one serialized backend event loop/actor that owns:
  - execution order state;
  - strategy state;
  - portfolio state;
  - canonical persistence ordering.
- [ ] Route real-time **trade events** to the Live-Paper executor immediately.
- [ ] Route **completed strategy candles** separately to `strategy.on_candle`.
- [ ] Route `on_start` order intents immediately into the Live-Paper executor.
- [ ] When the executor produces a fill:
  1. persist Fill / OrderState;
  2. apply it to the shared portfolio;
  3. persist Position / Equity effects;
  4. update the runtime snapshot/UI stream.
- [ ] Define deterministic ordering for market events that share timestamps and preserve canonical `run_sequence`.
- [ ] Keep Bot concurrency and one-active-Run-per-Bot guarantees unchanged.
- [ ] Keep immediate Start semantics from Phase 5C: the initial grid is created immediately from completed information, after which its resting orders are live-event driven.
- [ ] Do not change Backtest chronology in this phase.

### Future strategy hook

- [ ] Design the runtime boundary so a later shared `strategy.on_fill(...)` hook can be added once for strategies that replenish/recenter after fills.
- [ ] Do **not** invent replenishment rules for the current static-grid fixture; it still places its initial grid once.

**Checkpoint:** Live-Paper strategy decisions and live order execution have separate clocks but one deterministic Run state machine.

---

## Phase 5 — Backtest isolation, tests, and parity rules

Backtest remains a historical simulator. It should not be distorted to imitate real-time Paper limitations, and Live-Paper should not be degraded to candle execution merely to preserve old fill parity.

- [ ] Leave the current Backtest historical bar executor behavior unchanged:
  - resting BUY limit + candle low touch => fill under Touch;
  - resting SELL limit + candle high touch => fill under Touch;
  - historical fill timing remains limited by the available dataset.
- [ ] Keep future historical **tick-data execution** as a separate optional Backtest adapter that can be added later without changing strategy code.
- [ ] Update automated parity tests so they compare what should actually be common:
  - strategy decisions for identical strategy information;
  - order intents/configuration;
  - accounting given identical fills;
  - persistence invariants.
- [ ] Stop requiring candle-based Paper fills to match Backtest fill timing when Paper has richer live event information.
- [ ] Add focused Live-Paper tests for:
  - immediate Touch fill before candle close;
  - Trade Through strict inequality;
  - latency eligibility;
  - partial fills across qualifying events;
  - no pre-eligibility fill;
  - duplicate-trade suppression;
  - stop prevents later fills;
  - reconnect/gap failure/recovery contract.
- [ ] Keep the full frozen XAGUSDT Backtest regression unchanged and green.
- [ ] Add a deterministic synthetic test where the same static-grid strategy creates identical initial order intents in Backtest and Live-Paper, while the two executors legitimately determine fills from their own data source.

**Checkpoint:** Tests prove shared strategy semantics without falsely forcing Backtest and Live-Paper execution clocks to be identical.

## Phase 6 — Trading-page integration + production acceptance

No major Trading-page redesign is required. The UI should simply reflect fills when the backend actually creates them.

- [ ] Verify an active grid line disappears/updates immediately after the qualifying live trade, without waiting for the 1-minute candle to close.
- [ ] Verify fill marker, Position, PnL, Open Orders, and Run Activity update from that same fill event.
- [ ] Keep Run Activity newest-first and keep Technical audit diagnostic-only.
- [ ] Show execution latency/partial-fill assumptions exactly as configured; do not display a candle-close dependency because none exists.
- [ ] Production smoke test with an order level intentionally close enough to market to observe a real qualifying Touch.
- [ ] Compare the qualifying Binance trade timestamp with the persisted fill timestamp and confirm the fill occurred before the candle close when the touch happened intrabar.
- [ ] Verify browser close/reopen does not affect execution.
- [ ] Run two different Live-Paper Bots concurrently and verify no cross-Run trade/fill contamination.
- [ ] Update `Documents/ARCHITECTURE.md` after implementation with the final **shared strategy → mode-specific executor → shared accounting/persistence** architecture.

**Checkpoint:** The hosted Live-Paper grid behaves like a simulated live exchange account: resting orders react to live Binance events immediately, while strategy candle logic remains independent.

---

## Final acceptance

This roadmap is complete only when all of the following are true:

1. There is still exactly **one** implementation of the current static-grid strategy.
2. Backtest continues to use historical execution assumptions appropriate to its historical data.
3. Live-Paper no longer waits for candle close to execute resting grid orders.
4. Artificial execution behavior in Live-Paper comes only from explicitly configured assumptions such as latency, partial fills, fees, or fill policy.
5. Strategy-generated order intents, resulting fills, portfolio accounting, and canonical persistence remain auditable through the same shared contracts.
6. The frozen historical Backtest regression remains unchanged.
7. Phase 6 Console work and final Phase 4 production acceptance resume only after this execution-correctness roadmap passes.
