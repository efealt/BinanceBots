# Phase 4.8B — Trading workspace + persistent bots

## Objective

Turn Trading into the operational home for persistent trading bots.

A **Bot** is a saved trading configuration with its own identity and name. A **Run** is one execution session of that bot. Saving a bot must not start trading; starting a bot creates a new immutable run linked to that bot.

Backtesting remains a separate system and separate page. This roadmap is only for forward Paper execution now and the same bot/workspace model that Live execution can use later when Live is unlocked.

## Foundation already complete

The following work is already implemented and is no longer part of the remaining sequence:

- The Trading workspace no longer presents old terminal runs as if they are the current active bot.
- The selected registered Binance market streams on the Trading page before any Paper run exists.
- Trading uses the same Lightweight Charts engine and MarketChart wrapper as the working Market page, with native crosshair, zoom, pan, price scale, live candle updates, and trading overlays.
- Symbol/Market choices come from the SQLite-backed registered Binance dataset catalog.
- The page follows the responsive/fluid layout rule in `AGENTS.md`.

## Rules

- Complete the phases below strictly in order and stop after each phase for user review.
- A Bot is an identity + saved configuration. Symbol, market, strategy, grid settings, capital, execution assumptions, and similar values are parameters of that bot; they do not define what a Bot is.
- A Run is immutable historical execution state. Every new run created after the Bot layer is introduced must belong to a bot.
- Existing historical runs must not be silently assigned to a bot. They may remain legacy/unassigned history.
- Saving a bot must never create a run or place/simulate orders.
- Starting Paper must create a new run linked to the selected bot and freeze the exact configuration used by that run.
- One bot may have at most one active run at a time. Different bots may run concurrently.
- Closing or refreshing the browser must not stop any backend-owned run.
- Live execution remains server-side locked until its later roadmap phase. The Bot model and UI should remain mode-neutral so Live can use the same structure later, but this roadmap must not unlock Live.
- Backtests remain completely separate from Bots/Runs on this page.
- Responsive/fluid layout remains mandatory; no viewport-level horizontal scrolling.
- Do not change strategy rules or execution chronology while implementing the Bot/workspace model.

## Sequential phases

### Phase 1 — Persistent Bot identity and saved configuration

- [ ] Add persistent Bot storage with a stable `bot_id`, editable `bot_name`, saved configuration, and created/updated timestamps.
- [ ] Saved configuration must preserve the complete current Trading setup needed to restore the form: instrument parameters, strategy and strategy parameters, replay interval, capital, and execution assumptions.
- [ ] Add protected backend APIs to create, list, read, and update bots. Deletion is out of scope for this phase.
- [ ] Add `bot_id` linkage to trading runs. Existing historical runs remain valid legacy runs without an invented bot association.
- [ ] Require every newly created Paper run to reference a real persisted bot.
- [ ] Keep each run's existing immutable configuration snapshot even though the parent Bot may later be edited.
- [ ] Add storage/API tests proving: a bot can be saved without a run; editing a bot does not rewrite prior runs; and new runs retain their own frozen configuration.

**Exit:** A named bot can exist persistently with saved parameters even if it has never traded, and new runs can be canonically linked to that bot.

### Phase 2 — Bot strip and selected workspace

- [ ] Add a compact **Bots** strip near the top of Trading.
- [ ] If there are no bots, show a clear **No bots created** state and keep the configuration area available for creating one.
- [ ] Each bot card must show only useful operational identity/status: bot name, bot ID, current state (`Idle`, `Running · Paper`, future `Running · Live`), and active run ID when one exists.
- [ ] Running bots appear first; idle/saved bots remain visible after them.
- [ ] Clicking a bot card selects that bot and loads its saved configuration into the strategy controls.
- [ ] If the selected bot has an active Paper run, load that run's current execution state, portfolio, orders, chart overlays, and run activity.
- [ ] If the selected bot is idle, show its saved configuration with empty execution-state panels while the live market chart continues.
- [ ] Add a **New Bot** action that opens an unsaved configuration state without disturbing already-running bots.
- [ ] Add **Save Bot** so a new or edited bot can be persisted without starting it.
- [ ] Track edits to a saved bot as **Unsaved changes** until explicitly saved.
- [ ] Reloading the page must reconstruct the Bot strip from backend state and show any still-running bots without requiring the original browser session.

**Exit:** Trading opens as a bot workspace: saved/running bots are visible at the top, selecting one restores the correct bot, and a bot can be created/saved without executing it.

### Phase 3 — Bot-aware run lifecycle and concurrent Paper bots

- [ ] Starting Paper from a saved bot creates a new run linked to that bot.
- [ ] Starting from a brand-new unsaved configuration must use an explicit create-and-start flow so the run never becomes anonymous.
- [ ] Starting from an edited existing bot must make the save/start behavior explicit; do not silently execute configuration that the UI still labels as the saved bot version.
- [ ] Enforce one active run per bot while allowing different bots to run concurrently.
- [ ] Stop affects only the selected bot's active run; the Bot itself remains saved and returns to `Idle`.
- [ ] After Stop, the completed run remains under that bot's history and a later Start creates a new run ID under the same bot.
- [ ] Closing/reopening Trading must show all backend-owned running Paper bots in the Bot strip and allow switching between them without affecting execution.
- [ ] Ensure the current Paper manager, streams, snapshots, chart overlays, audit, and portfolio state are routed by the selected bot's active `run_id`, not by a single global “current run.”
- [ ] Add concurrency tests with at least two different Paper bots active simultaneously and prove their orders/fills/portfolio/audit state cannot cross-contaminate.

**Exit:** Multiple saved bots may exist, multiple different Paper bots may run concurrently, and each bot cleanly owns its own sequence of runs.

### Phase 4 — Pre-trade “Show on graph” preview for the selected bot

- [ ] Add **Show on graph** beside the selected bot's run controls.
- [ ] Preview uses the visible working configuration and the same strategy/grid semantics as Paper start.
- [ ] Preview returns visual levels only; it must not create a run, order, fill, position, audit event, or mutate the saved bot.
- [ ] Draw preview levels on the already-live Lightweight Charts view with unmistakable **Preview · not active** styling.
- [ ] After a preview exists, changing any strategy-defining parameter immediately marks it **stale**.
- [ ] A stale preview may remain visible, but the action must change to a warning-style **Update preview** state and the old levels must not look current.
- [ ] Pressing **Update preview** recalculates from the current controls.
- [ ] Starting Paper must execute the explicit current/saved configuration and replace preview levels with canonical run overlays.
- [ ] Add parity coverage proving the previewed initial grid matches the initial grid created by Paper for the same configuration and market boundary.

**Exit:** The selected/new bot can be configured, previewed on live market data, updated safely after edits, then explicitly saved and/or started.

### Phase 5 — Bot history, run activity, and compact workspace layout

- [ ] Use clear UI terminology:
  - **Execution state** = current open orders/current execution state of the selected active run.
  - **Run activity** = event/fill audit for the selected run.
  - **Bot history** = the list of previous runs belonging to the selected bot.
- [ ] Add Bot history for the selected bot with run ID, mode, start/stop time, terminal status, and core result summary; selecting a historical run is inspection-only and must not make it look active.
- [ ] Preserve access to the complete canonical event/fill audit for any selected historical run.
- [ ] Move compact runtime/configuration context to the top workspace near Bot/Runtime health instead of keeping the large bottom Runtime context panel.
- [ ] Redesign Position and account state as one compact wide row on large desktop displays, progressively wrapping at narrower widths.
- [ ] Remove duplicated/obsolete status cards and the old bottom Runtime context panel once the top Bot workspace is authoritative.
- [ ] Keep the Trading chart continuously available while switching between idle bots, active bots, and historical-run inspection.
- [ ] Do not remove the existing Console yet. Once Trading fully covers bot orchestration, treat Console removal/deprecation as a separate explicit cleanup decision.

**Exit:** The selected bot has understandable current execution state, current-run activity, and historical runs without confusing any of them with each other, and the page remains compact and responsive.

### Phase 6 — Integrated production acceptance

- [ ] Verify a brand-new bot can be configured and **Save Bot** creates it without creating a run.
- [ ] Reload Trading and verify the saved idle bot appears in the Bot strip and restores its saved configuration.
- [ ] Preview that bot on the live chart and verify no run/events are created.
- [ ] Start Paper and verify a new run linked to that bot appears as `Running · Paper`.
- [ ] Close/reopen the page and verify the backend run continues and the Bot strip restores it correctly.
- [ ] Create/save a second bot and run it concurrently; switch between both and prove portfolio/orders/chart overlays/run activity remain isolated.
- [ ] Stop one bot and verify the other continues unaffected.
- [ ] Restart the stopped bot and verify a new run ID is added under the same Bot history.
- [ ] Verify idle, running, preview, stale-preview, stopped, and historical-inspection UI states.
- [ ] Verify the page at wide 4K-style desktop width and progressively narrower widths with no viewport-level horizontal scrolling.
- [ ] Update `Documents/ARCHITECTURE.md` and the parent Phase 4 roadmap with the final Bot → Run architecture.

**Exit:** Trading is a persistent multi-bot operational workspace: bots can be saved without running, Paper bots can run concurrently, every execution is a run under a bot, history is preserved, and the browser is only an operational client.
