# Phase 4.8B — Trading workspace + persistent bots

Status: COMPLETE

## Objective

Turn Trading into the operational home for persistent trading bots.

A **Bot** is a saved trading configuration with its own identity and name. A **Run** is one execution session of that bot. Saving a bot must not start trading; starting a bot creates a new immutable run linked to that bot.

Backtesting remains a separate system and separate page. This roadmap is only for forward **Live-Paper** execution now and the same bot/workspace model that **Live-Real-Account** execution can use later when it is explicitly unlocked.

## Foundation already complete

The following work is already implemented and is no longer part of the remaining sequence:

- The Trading workspace no longer presents old terminal runs as if they are the current active bot.
- The selected registered Binance market streams on the Trading page before any Live-Paper run exists.
- Trading uses the same Lightweight Charts engine and MarketChart wrapper as the working Market page, with native crosshair, zoom, pan, price scale, live candle updates, and trading overlays.
- Symbol/Market choices come from the SQLite-backed registered Binance dataset catalog.
- The page follows the responsive/fluid layout rule in `AGENTS.md`.

## Rules

- Complete the phases below strictly in order and stop after each phase for user review.
- A Bot is an identity + saved configuration. Symbol, market, strategy, grid settings, capital, execution assumptions, and similar values are parameters of that bot; they do not define what a Bot is.
- Bot identity remains user-defined, but Trading treats **Symbol**, **Market**, and **Strategy** as identity-sensitive edits. Saving those changes to an existing Bot requires an explicit choice: cancel, update the same Bot, or create a brand-new Bot from the edited form. Creating a new Bot never carries Run history from the source Bot.
- A Run is immutable historical execution state. Every new run created after the Bot layer is introduced must belong to a bot.
- Development trading state from before the Bot model is removed rather than carried forward. Downloaded market datasets remain untouched.
- Saving a bot must never create a run or place/simulate orders.
- Starting Live-Paper must create a new run linked to the selected bot and freeze the exact configuration used by that run.
- One bot may have at most one active run at a time. Different bots may run concurrently.
- Closing or refreshing the browser must not stop any backend-owned run.
- **Live-Real-Account** execution remains server-side locked until its later roadmap phase. **Live-Paper** is the current in-scope forward execution mode. The Bot model and UI must remain mode-neutral so Live-Real-Account can use the same structure later, but this roadmap must not unlock real-account order submission.
- Backtests remain completely separate from Bots/Runs on this page.
- Responsive/fluid layout remains mandatory; no viewport-level horizontal scrolling.
- Do not change strategy rules or execution chronology while implementing the Bot/workspace model.

## Sequential phases

### Phase 1 — Persistent Bot identity and saved configuration

- [x] Add persistent Bot storage with a stable `bot_id`, editable `bot_name`, saved configuration, and created/updated timestamps.
- [x] Saved configuration must preserve the complete current Trading setup needed to restore the form: instrument parameters, strategy and strategy parameters, replay interval, capital, and execution assumptions.
- [x] Add protected backend APIs to create, list, read, and update bots. Deletion is out of scope for this phase.
- [x] Add `bot_id` linkage to trading runs and clean pre-Bot trading history from the development database while preserving downloaded datasets.
- [x] Require every newly created Live-Paper run to reference a real persisted bot.
- [x] Keep each run's existing immutable configuration snapshot even though the parent Bot may later be edited.
- [x] Add storage/API tests proving: a bot can be saved without a run; editing a bot does not rewrite prior runs; and new runs retain their own frozen configuration.

**Exit:** A named bot can exist persistently with saved parameters even if it has never traded, and new runs can be canonically linked to that bot.

**Implemented:** Migration 005 adds `trading_bots` and `trading_runs.bot_id`. Migration 006 resets Trading operational state while preserving Data Downloader definitions and downloaded historical market datasets. Bot records persist a stable ID/name and the complete validated Trading configuration. Protected bot create/list/read/update APIs save configuration without creating a run. Every Live-Paper run requires an explicit persisted `bot_id`, and each run keeps its own immutable strategy/config/data-source/execution snapshot. Backtests remain separate and may create run records without a Bot.

- [x] If the selected bot is idle, show its saved configuration with empty execution-state panels while the live market chart continues.

- [x] Add **Save Bot** so a new or edited bot can be persisted without starting it.

**Exit:** Trading opens as a bot workspace: saved/running bots are visible at the top, selecting one restores the correct bot, and a bot can be created/saved without executing it.

**Implemented:** Trading now loads `/api/trading/bots` together with Live-Paper run summaries and renders a compact Bot strip with running Bots first. Bot cards show Bot name/ID plus `Idle` or `Running · Live-Paper` and active Run ID. Selecting a Bot restores its saved configuration and, when active, its current snapshot/portfolio/orders/chart overlays/run activity. Idle Bots keep the real-time market chart while execution panels remain empty. **New Bot** opens an unsaved draft without stopping backend-owned runs, and **Save Bot** persists create/update state without creating a Run. Saved-Bot edits are marked **Unsaved changes** and cannot start Live-Paper until saved. Page reload reconstructs Bot state from the backend and automatically selects a running Bot first when one exists. Editing ordinary parameters continues to update the selected Bot normally. Editing Symbol, Market, or Strategy now opens an identity safeguard before Save or Save & Start: the user may cancel, explicitly update the same Bot, or name and create a fresh Bot directly from the unsaved form. The fresh Bot starts with no Run history; the source Bot and all frozen Runs remain untouched. Phase 2 deliberately retains the current single-active-Live-Paper runtime limit; multi-Bot concurrency is Phase 3.

### Phase 3 — Bot-aware run lifecycle and concurrent Live-Paper bots

- [x] Starting Live-Paper from a saved bot creates a new run linked to that bot.
- [x] Starting from a brand-new unsaved configuration must use an explicit create-and-start flow so the run never becomes anonymous.
- [x] Starting from an edited existing bot must make the save/start behavior explicit; do not silently execute configuration that the UI still labels as the saved bot version.
- [x] Enforce one active run per bot while allowing different bots to run concurrently.
- [x] Stop affects only the selected bot's active run; the Bot itself remains saved and returns to `Idle`.
- [x] After Stop, the completed run remains under that bot's history and a later Start creates a new run ID under the same bot.
- [x] Closing/reopening Trading must show all backend-owned running Live-Paper bots in the Bot strip and allow switching between them without affecting execution.
- [x] Ensure the current Live-Paper manager, streams, snapshots, chart overlays, audit, and portfolio state are routed by the selected bot's active `run_id`, not by a single global “current run.”
- [x] Add concurrency tests with at least two different Live-Paper bots active simultaneously and prove their orders/fills/portfolio/audit state cannot cross-contaminate.

**Exit:** Multiple saved bots may exist, multiple different Live-Paper bots may run concurrently, and each bot cleanly owns its own sequence of runs.

**Implemented:** Live-Paper runtime admission is now Bot-aware and race-safe: a Bot can own at most one `arming`/running Run while different Bots can execute concurrently (subject to the production runtime cap). Each Run remains keyed by its own `run_id`, with independent backend snapshot, WebSocket stream, portfolio, orders, fills, chart overlays, and audit trail. Trading can switch between running Bot cards without stopping their backend runtimes; Stop targets only the selected Run. Starting a new draft is explicitly **Create & Start Live-Paper** (persist Bot first, then Run), while edited saved Bots use **Save & Start Live-Paper** so the executed configuration is never silently different from the saved Bot. Restarting an idle Bot creates a new immutable Run ID under the same Bot. Focused tests run two Bot cores simultaneously and verify their orders, fills, portfolios, events, and canonical audit pages remain isolated.

- [x] Pressing **Update preview** recalculates from the current controls.
- [x] Starting Live-Paper must execute the explicit current/saved configuration and replace preview levels with canonical run overlays.
- [x] Add parity coverage proving the previewed initial grid matches the initial grid created by Live-Paper for the same configuration and market boundary.

**Exit:** The selected/new bot can be configured, previewed on live market data, updated safely after edits, then explicitly saved and/or started.

**Implemented:** `POST /api/trading/preview` validates the visible Live-Paper configuration and derives preview levels in memory from the same `StaticGridStrategy::on_start` semantics used by execution. It creates no Bot, Run, order, fill, position, audit event, or portfolio mutation. Previous-close previews use the latest fully-known replay boundary and report that reference boundary explicitly. Live-Paper Start now uses that same current-boundary rule and creates the initial grid immediately from the latest completed replay candle; it no longer waits for the next replay boundary. The Trading page draws dotted **PREVIEW** BUY/SELL levels on the already-live Lightweight Charts view with a persistent **Preview · not active** badge. Strategy-defining edits mark the preview stale and switch the action to warning-style **Update preview**; switching Bot/New Bot clears the old preview, and an active Live-Paper snapshot replaces preview overlays with canonical Run overlays. Rust parity coverage compares preview levels with the persisted initial Live-Paper orders for the same configuration, previous candle, and boundary.

### Phase 5 — Bot history, run activity, and lower-workspace cleanup

Phase 5 is intentionally split so data/history semantics are stabilized before any lower-workspace redesign.

**Frozen during Phase 5:** the top **Bots strip**, **Live-Paper controls / Strategy configuration**, and **Shared market monitor** are already accepted and should not be redesigned. Change them only if a Phase 5 integration bug requires a minimal fix.

#### Phase 5A — Backend history + activity data contract

- [x] Add a Bot-history query/API keyed by `bot_id`, returning that Bot's Runs newest first with Run ID, mode, created/start/end times, canonical/runtime status, and a compact result summary suitable for the UI.
- [x] Include useful terminal/current Run summary fields without requiring the browser to reconstruct them from the complete audit: fill count, ending position, fees paid, realized PnL, and ending/latest equity when available.
- [x] Keep every Run immutable and inspectable by `run_id`; selecting historical data must never change Bot state or create/stop execution.
- [x] Add a presentation-oriented **Run activity** contract derived from canonical persisted events:
  - newest meaningful action first;
  - prioritize lifecycle, order, fill, position, error/warning, and material execution events;
  - suppress repetitive equity-only heartbeat rows from the default activity view;
  - do **not** delete, rewrite, or weaken the canonical audit.
- [x] Preserve access to the complete canonical event/fill audit for any Run, including historical Runs. Canonical sequence remains the source of truth even if the default activity view is filtered/reordered for readability.
- [x] Add backend tests proving Bot history is isolated by `bot_id`, sorted newest first, summaries belong to the correct Run, and the quieter activity view never changes the underlying canonical event record.
- [x] Do not change Live-Paper execution behavior, strategy semantics, portfolio accounting, fills, order lifecycle, or concurrency in Phase 5A.

**Implemented:** Bot history is now exposed at `GET /api/trading/bots/{bot_id}/runs`, newest Run first, with canonical/runtime status plus persisted fill count, latest position, fees, realized PnL, and latest equity. Presentation activity is exposed at `GET /api/trading/runs/{run_id}/activity`, newest meaningful event first; Equity heartbeat events are suppressed only from this view and counted explicitly as suppressed. Older activity can be paged with `before_sequence`. The existing canonical `/audit` route and underlying event sequence are unchanged. Storage tests prove Bot isolation, newest-first ordering, correct per-Run summaries, activity filtering/order, and canonical non-mutation.

**5A exit:** The backend exposes clean Bot history and presentation-ready Run activity while preserving the complete canonical audit unchanged.

The lower workspace uses a compact Portfolio monitor, separate responsive BUY/SELL order columns with one card per exact backend order; untouched orders show a simple **Qty · Open** state, while partial fills show **Filled / original · Remaining** only when those distinctions matter, a newest-first Run activity timeline backed by the Phase 5A activity contract, and on-demand canonical audit. Historical inspection also switches the live market chart to the inspected Run's symbol/market when available, without editing the saved Bot configuration. Wide/narrow layouts use bounded grids and wrap/stack rather than page-level horizontal scrolling.

**5B exit:** The lower Trading workspace is compact and operational: portfolio state is easy to scan, open BUY/SELL orders are compact, newest Run activity is immediately visible, noise is reduced, and Bot history is clear without changing the accepted top Trading workflow.
